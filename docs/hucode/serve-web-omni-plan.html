Implementation Plan

Omni Projects View for hucode serve-web

A phased plan for adding stable Omni and workbench web routes while preserving regular VS Code web workbench behavior at root by default.

Default: regular serve-web Omni route: /omni Workbench route: /workbench --omni swaps root Hosted workbenches: iframes Scope: server-web archive

Objective

Change hucode serve-web so it always exposes a Hucode Omni Projects shell at /omni and a normal VS Code web workbench at /workbench. The default root route should continue to serve the regular VS Code web workbench.

When --omni is passed, only the root route changes: / should serve the same Omni shell that is already available at /omni. Regular individual workbenches must remain available at explicit /workbench URLs, including folder, workspace, and empty-window URLs.

Success Criteria

  • hucode serve-web keeps printing and serving the regular root workbench by default.
  • /omni serves the Omni shell whether or not the CLI was launched with --omni.
  • hucode serve-web --omni makes root serve the Omni shell instead of the regular workbench.
  • /workbench?folder=/path/to/project loads a normal VS Code web workbench for that folder.
  • /workbench?ew=true loads a normal empty VS Code web workbench.
  • The Omni shell can open, switch, hide, and close hosted workbenches without replacing the browser page.
  • The Omni shell preserves desktop Omni command-routing semantics where browsers permit it, using iframe messaging instead of Electron WebContentsView APIs.
  • The server-web release archive contains every new HTML, JavaScript, CSS, and static resource needed by Omni web.

Current State

The Rust CLI command is a server-of-servers. It validates license and prerequisites, creates or reads a shared connection token, starts a versioned server-web process, and proxies HTTP and WebSocket traffic over a socket.

The Node server currently serves the web workbench HTML only at / after base-path and product-path stripping. It also serves /static/*, /callback, and /web-extension-resource/*. Paths such as /omni and /workbench are not currently valid HTML routes.

Normal web workbench selection is query-driven. A folder URL uses ?folder=/repo, a workspace URL uses ?workspace=/repo/foo.code-workspace, and an empty window uses ?ew=true. When none of those are present, server-provided default-folder or default-workspace config is used.

Desktop Omni is not a normal workbench overlay. It has its own renderer entrypoint and shell bootstrap. The hosted desktop workbenches are native Electron WebContentsView instances, controlled by an Electron main-process shell service. The web version cannot reuse that containment model.

Keep /workbench deliberately boring. It should serve the same normal web workbench template as upstream /, only with a different pathname. It should be available in both modes so Omni can host direct workbench URLs and users can load a workbench without changing root behavior.

Canonical routes are /omni and /workbench. Accept trailing-slash aliases only as redirects to the canonical paths, preserving all query parameters and base-path prefixes.

The current server CSP already permits same-origin frames with frame-src 'self' and child-src 'self'. That keeps iframe hosting feasible, but it does not solve lifecycle, focus, dirty-state, or storage isolation.

Shared Cores And Adapters

The web implementation should not copy desktop Omni systems wholesale. Extract platform-neutral behavior first, then inject small adapters for Electron desktop and browser/server-web differences.

Phased Plan

Phase 0 - Confirm Constraints

Goal: reduce hidden coupling before writing code.

  1. Re-run a source pass over current serve_web.rs, webClientServer.ts, Omni shell, and build entrypoint files.
  2. Decide the flag name. Recommended: --omni, because it is concise and only changes the root route target.
  3. Confirm route names. Recommended: /omni for the Projects shell and /workbench for direct workbench loads, with root staying regular by default and becoming Omni only when the flag is present.
  4. Confirm that root token cleanup can preserve non-token query parameters when redirecting.
  5. Identify the minimum shared-core extractions before web work starts: route decisions, hosted-workbench descriptors, hosted-workspace controller state, and project-manager core.

Tests: none yet, but record decisions in the implementation PR description.

Phase 1 - CLI And Server Routing

Goal: make stable routes and root selection explicit.

  1. Add omni: bool to ServeWebArgs in the Rust CLI.
  2. Forward the flag to the spawned server-web entrypoint as a Hucode-owned server argument, for example --hucode-web-omni-root.
  3. Add the server argument to ServerParsedArgs and the server option table. Keep the name Hucode-specific to avoid colliding with upstream VS Code options.
  4. Refactor WebClientServer root handling so it can dispatch root, /omni, and /workbench, but keep Hucode decisions in a companion such as src/vs/server/node/hucodeWebOmniRoutes.ts.
  5. Add /omni as the stable Omni shell route in both modes.
  6. Add /workbench as the stable normal workbench route in both modes.
  7. Add canonicalization redirects from /omni/ to /omni and from /workbench/ to /workbench, preserving query parameters and server-base-path prefixes.
  8. Update printed CLI URL. The CLI can keep printing root; --omni only changes what root serves.

Tests: add Node route tests around WebClientServer if a local test seam exists; add Rust unit coverage for flag parsing and forwarding if the CLI test harness can exercise ServeWebArgs without starting a real server.

Phase 2 - Shared Core Boundaries

Goal: prevent desktop/web duplication before adding web host code.

  1. Extract a hosted-workspace controller core that owns instance IDs, active selection, lifecycle state, visibility intent, close/reload/unload transitions, and event emission.
  2. Define a hosted-workspace host adapter interface for create, navigate, show, hide, focus, reload, and dispose operations. Keep screenshot capture as an optional desktop-only capability, not a shared web requirement.
  3. Move hosted-workbench target-to-descriptor and descriptor- to-URL decisions into shared helpers that both desktop and web can call.
  4. Extract project-manager record/state logic away from Electron-only construction so desktop and server can share normalization, ordering, labels, pins, visits, and refresh semantics.
  5. Define shared hosted-workbench message payloads for ready, focus, dirty, unload, crash, and status reporting.
  6. Extract or extend the shared Omni command-routing policy so desktop and web agree on shell-owned commands, layout actions, forwarding guards, and forwarded-request markers.

Tests: add core unit tests before platform adapters. Cover lifecycle transitions once, then add smaller adapter conformance tests for desktop and web behavior.

Phase 3 - Omni Web Entrypoint

Goal: boot an Omni shell page in browser/server-web.

  1. Create a web shell bootstrap near the existing Hucode Omni entrypoints. Candidate names: src/vs/hucode/omni.web.main.ts and a Hucode-owned HTML template such as src/vs/hucode/browser/omni-web.html.
  2. Keep the shell close to a real workbench bootstrap, as desktop Omni does. Reuse Hucode-owned browser parts where layering allows.
  3. Do not parameterize upstream src/vs/code/browser/workbench/workbench.html unless the Hucode-owned template path proves unworkable.
  4. Inject web configuration with a payload that marks the root renderer as isOmniWindow=true.
  5. Add a browser-safe shell service implementation that implements the shared IHucodeShellService contract without Electron APIs.
  6. Implement the service methods needed for desktop-equivalent Projects, lifecycle, focus, reload, and command routing. Return no-ops only for behavior classified as Electron-only with no browser equivalent.

Tests: browser unit tests for service state transitions and context keys. Avoid brittle full-DOM assertions until the route is loading end to end.

Phase 4 - Iframe Hosted Workbench Adapter

Goal: replace Electron WebContentsView hosting with same-origin iframes.

  1. Create a web hosted-workbench adapter for the shared hosted workspace controller core, scoped to browser primitives.
  2. Key resident hosted workbenches by normalized worktree path through the shared core, matching the desktop model.
  3. Generate iframe URLs against the explicit workbench route: /workbench?folder=/path for folders and /workbench?ew=true for empty windows, using the shared descriptor helper.
  4. Use visibility toggles for resident inactive iframes. Keep them attached to preserve runtime state until the user explicitly closes that hosted workbench.
  5. Do not implement app-level iframe eviction. Browser tab discard is treated as a whole-shell reload concern, not as a per-workbench memory policy.
  6. Use postMessage between parent shell and hosted workbench to report readiness, focus, dirty state, unload intent, command requests, and shell-owned action requests.
  7. Add a web-only host-surface seam in the Hucode OmniHostPart if the iframe adapter needs to attach iframes under a real DOM parent. Keep desktop layout via bounds intact.
  8. Do not port the desktop screenshot overlay fallback to web. Shell overlays should sit above hosted iframes through normal DOM positioning and stacking.
  9. Add a hosted-web contribution loaded by normal web workbenches when a payload marks isHostedOmniWorkspace=true.
  10. Add browser environment payload getters for isHostedOmniWorkspace and hostedInstanceId before relying on existing hosted-workbench context keys.
  11. Implement same-origin focus transfer. The shell should focus the active iframe after selection and should restore Projects focus when requested.

Tests: browser tests for open, activate, reuse existing, close active, close last, and crashed iframe state. Add Playwright coverage once the dev server can serve the route.

Phase 5 - Project Manager On Server-Web

Goal: make Projects sidebar useful in browser-only Omni.

  1. Use the extracted project-manager core from Phase 2 so the server implementation shares record normalization, ordering, labels, pins, visits, and refresh semantics with desktop.
  2. Add a Hucode-owned project-manager channel and client for the existing PROJECT_MANAGER_CHANNEL_NAME.
  3. Register the channel from serverServices.ts through a Hucode companion function, keeping the upstream file to service creation plus one registration call.
  4. Add a browser-side client registration for IProjectManagerService in the Omni web entrypoint.
  5. Persist server-web project metadata under the server data dir. Recommended path shape: <server-data-dir>/hucode/projects.json or a Hucode-owned state file under <server-data-dir>/data; keep it separate from browser localStorage and client-side settings.
  6. Start server-web with an empty project registry. Do not migrate or import desktop Omni project state; this matches existing serve-web behavior, which does not migrate desktop user settings or state into the web server environment.
  7. Do not fold future server-side user data/settings storage into this work. Project metadata is a Hucode server-side registry; user settings/profile persistence is a later, separate serve-web enhancement.
  8. Keep worktree watchers server-side so one project registry feeds all iframe workbenches and the shell.

Tests: node unit tests for server project manager persistence and channel methods. Reuse existing project-manager test fixtures where possible.

Phase 6 - Build And Packaging

Goal: ship the new web shell in server-web archives.

  1. Add the Omni web entrypoint to the server-web bundle path in build/next/index.ts.
  2. Add the entrypoint to CSS bundling if it imports CSS.
  3. Update legacy gulp build lists if they remain active for vscode-reh-web-*-min-ci.
  4. Ensure HTML templates and any static assets are copied into out-vscode-reh-web* and the packaged vscode-reh-web-* archive.
  5. Verify Hucode product mixin staging still applies while server-web is packaged.

Tests: run the server-web bundle target used by Hucode CI, then inspect the output archive for Omni web JavaScript, CSS, and HTML.

Phase 7 - Lifecycle And Command Polish

Goal: make the shell reliable under real use.

  1. Implement hosted workbench unload negotiation before removing an iframe.
  2. Inventory the current desktop Omni command-forwarding paths and maintain a parity matrix: browser-supported, naturally handled by iframe focus, browser fallback, or Electron-only no-op.
  3. Forward shell commands that desktop would route to the active hosted workbench, while keeping Projects and other shell-owned commands local.
  4. Support hosted workbench to shell forwarding for Projects sidebar commands, navigation affordances, and shell-owned actions that already route back to desktop Omni.
  5. Keep QuickInput and context menus local to the renderer that opened them. Do not forward commands while shell QuickInput or local shell input has focus.
  6. Let a focused hosted iframe handle normal workbench keybindings directly. Forward keybinding-originated commands only when focus is in the shell and the routing policy says the active workbench should handle the command.
  7. Handle paste as focus handoff plus browser-native paste where possible. Do not depend on synthetic paste events matching Electron webContents.paste().
  8. Handle iframe navigation failure as crashed or unloaded state in Projects UI.
  9. Handle whole-tab discard/restore using lifecycle signals such as document.wasDiscarded where available. After restore, rebuild shell state from the server-side project registry rather than assuming resident iframes survived.
  10. Detect individual hosted-workbench failure with readiness timeouts, load errors where observable, and optional heartbeat messages. Treat failures as reloadable hosted-workbench state, not as a reason to evict other iframes.
  11. Review localStorage and IndexedDB behavior when several same-origin workbenches are loaded at once.

Tests: integration tests for project switch, reload active workbench, close active workbench, dirty unload, shell-to-workbench command forwarding, workbench-to-shell action forwarding, keybinding focus cases, paste fallback, and no-workbench command behavior.

Risks And Mitigations

Risk Impact Mitigation
Desktop/web controller drift Copying the desktop controller into a web controller creates two lifecycle systems that diverge under close, reload, dirty-unload, and crash handling. Extract a shared hosted-workspace core first, then require desktop WebContentsView and web iframe adapters to pass the same lifecycle conformance tests. Keep Electron-only screenshot fallback outside the shared core.
Accidental screenshot dependency on web Web implementation could inherit desktop screenshot polling even though iframes can be layered under shell DOM directly. Treat capture as an optional desktop adapter capability. Web overlays must use DOM stacking above the iframe host.
Iframe storage collisions Several workbenches share origin, cookies, localStorage, IndexedDB, and callback state. Audit workspace-scoped storage keys. Add hosted-workbench payload identity. Prefer server-side state for Projects.
Dirty unload Closing an iframe directly can lose state or edits. Add parent-child unload protocol before iframe removal. Treat missing response as a veto or timeout policy decision.
Browser tab discard The browser can discard or reload the whole Omni tab under resource pressure, taking the shell and all hosted iframes with it. Treat discard as whole-shell recovery. Use document.wasDiscarded where available and rebuild from server-side project state. Do not try to prevent or override browser discard.
Hosted iframe failure A hosted workbench iframe can fail to load, stop responding, or be reloaded independently of user intent. Track readiness, optional heartbeat, load failure, and reload state per hosted workbench. Surface it as reloadable state in Projects without closing unrelated iframes.
Command and keybinding ambiguity Shell commands can accidentally run in the hosted workbench, or hosted commands can run in the shell. Keep command routing command-id based and shared with the desktop policy. Scope shell-to-workbench forwarding to the active iframe only when shell focus is outside local inputs; route shell-owned commands locally.
Browser input trust and clipboard limits Browser pages cannot reliably synthesize trusted key or paste events into an iframe the way Electron can call native webContents APIs. Let focused iframes handle normal browser events directly. Use focus handoff for paste and document any Electron-only behavior as an explicit parity exception.
Project manager unavailable in web Projects sidebar is empty or actions fail. Promote project manager to a server node channel before treating Omni web as complete.
Project metadata mixed with user settings The implementation could accidentally couple Hucode project registry storage to future serve-web user settings/profile storage. Store project metadata in a Hucode-owned file under the server data dir. Keep server-side user data/settings persistence as a separate future feature.
Server-web archive misses assets Local dev works, released hucode serve-web 404s the Omni shell. Add archive inspection to validation and test the packaged server-web output, not only source dev mode.
Reverse proxy base-path regression Omni or iframe URLs fail under --server-base-path. Construct routes from server-provided base path. Include base-path cases in route tests.

Non-Negotiable Constraints

  • Do not change default hucode serve-web root behavior. Without --omni, root / must remain the regular VS Code web workbench.
  • Always expose the Omni Projects shell at /omni and a normal workbench at /workbench, regardless of whether --omni is present.
  • --omni only changes what root / serves. It must not hide or alter /workbench.
  • Canonical paths are /omni and /workbench. Trailing slash variants must redirect to canonical paths while preserving query parameters and --server-base-path.
  • Keep upstream VS Code files as thin integration points. Hucode routing, shell, lifecycle, project-manager, command routing, and iframe policy must live in Hucode-owned helpers or clearly named hucode* companions.
  • Do not copy the desktop hosted-workspace controller into a separate web controller. Extract shared state-machine logic first, then attach desktop and web adapters.
  • Use iframes for web hosted workbenches. Do not use Electron WebContentsView concepts in the web adapter.
  • Do not implement app-level iframe eviction. Hosted workbenches stay resident until the user closes them; browser tab discard is a whole-shell recovery concern.
  • Do not port desktop screenshot overlay fallback to web. Web shell overlays should layer above iframe workbenches through normal DOM stacking.
  • Project metadata for server-web belongs in a Hucode-owned file under the server data dir. Do not store it in browser localStorage, VS Code user settings, or client-side profile state.
  • Do not implement desktop-to-server project migration. Existing serve-web does not migrate desktop user data, and project metadata should follow that separation.
  • Preserve semantic parity with desktop Omni command routing where browsers permit it. Browser-only exceptions must be explicitly documented and tested.

  14. Handle browser exceptions explicitly: focused iframe keybindings are naturally local; paste uses focus handoff and browser-native behavior where possible; Electron native paste is not expected on web.
  15. Run unit, integration, and packaged server-web validation. Update Hucode CI wiring if new test files need to run in CI.

Testing Strategy

Unit And Component Tests

  • Route selection: default root regular, default /omni shell, --omni root shell, workbench folder URL, workbench empty URL, trailing-slash redirects, query preservation, base-path variants. Prefer Hucode-named tests around the new route helper instead of broad assertions against all of WebClientServer.
  • CLI forwarding: ServeWebArgs.omni defaults to false and sends --hucode-web-omni-root only when requested.
  • Shared hosted-workspace core: open, activate, reuse, hide, close active, close last, reload, dirty unload, crash/unload, browser-discard recovery, and event-order transitions without platform APIs.
  • Host adapter conformance: desktop and web adapters both satisfy create, navigate, show, hide, focus, reload, and dispose contracts against the same fake core tests. Cover screenshot capture only in desktop adapter tests.
  • Descriptor helpers: folder, workspace, empty-window, worktree, base-path, and hosted-payload cases produce matching desktop and web descriptors before adapter-specific URL/config mapping.
  • Web shell service: initial empty state, open workspace, reuse workspace, activate existing workspace, close active, close last workspace.
  • Iframe controller: URL generation, visibility transitions, readiness message handling, heartbeat timeout, failure state handling, explicit user close, and no automatic eviction.
  • Project manager server channel: get, add, refresh, move, rename, last-active update.
  • Command-routing policy: shell-owned commands stay local, workbench commands forward only when shell focus allows it, forwarded-request markers prevent loops, and layout actions match desktop handling.

Integration Tests

  • Launch server-web without the Omni flag and navigate to root. Assert the regular workbench appears.
  • Launch server-web without the Omni flag and navigate to /omni. Assert Omni shell and Projects sidebar appear.
  • Launch server-web with the Omni flag and navigate to root. Assert Omni shell and Projects sidebar appear.
  • Navigate to /workbench?folder=/tmp/foo. Assert regular workbench appears without Omni chrome.
  • Navigate to /workbench?ew=true. Assert regular empty workbench appears.
  • Navigate to /omni/?folder=/tmp/foo and /workbench/?folder=/tmp/foo. Assert each redirects to the no-trailing-slash canonical path while preserving folder.
  • From Omni Projects, select a worktree and assert an iframe loads a normal workbench.
  • Switch between two worktrees and assert the previous iframe stays resident but hidden.
  • Simulate hosted iframe readiness timeout or failed navigation and assert Projects shows a reloadable failure state without closing other hosted workbenches.
  • From Projects focus, invoke a workbench-owned command and assert it forwards to the active hosted iframe.
  • From hosted iframe focus, invoke a Projects/sidebar command and assert it forwards back to the shell.
  • Assert normal keybindings stay in the focused iframe, while shell-local inputs such as QuickInput do not forward.
  • Simulate shell restore after browser discard where possible, or unit-test the recovery path from document.wasDiscarded.
  • Run under --server-base-path /x and repeat root, /omni, and /workbench route checks.
  • Run at least one packaged server-web archive check, because hucode serve-web consumes downloaded archives, not only source-mode server output.

Open Decisions

None currently. Command forwarding is no longer a reduced first-release subset: the target is semantic parity with desktop Omni command routing, with explicit browser-only exceptions for Electron-native behavior such as trusted paste injection.

Recommended Order

  2. Extract shared hosted-workspace, hosted descriptor, route decision, project-manager, and message-contract cores with focused unit tests.
  3. Land inert Omni web shell at /omni with Projects chrome but no hosted workbench loading.
  4. Land --omni root swap once /omni is working.
  5. Land iframe hosted-workbench adapter with manual folder opening, backed by the shared hosted-workspace core and no automatic iframe eviction.
  6. Land server project-manager channel and full Projects sidebar integration on the shared project-manager core.
  7. Land lifecycle, unload, command routing, and packaging hardening.
